# 需求说明：按规则保存抓包响应，并按 URL 回放

本文只记录用户要的两件事、插件现在已经能做什么、以及还缺什么。产品上没有说死的选择一律标为「待确认」，本文不替产品做决定，也不改现有行为。

## 用户目标

1. 能保存「指定规则」匹配到的请求：把抓包响应落成以后可以回放的文件。
2. 之后能按 URL 自动匹配这些保存结果并回放（Mock）。

## 现状：已经能做什么

插件名 `whistle.sake`。`rules.txt` 里是 `* whistle.sake://none`，经过 whistle 的请求都会进入插件的保存钩子（`resStatsServer`）和动态规则钩子（`rulesServer`）。规则存在 whistle 的插件存储里，配置界面通过 `uiServer` 读写。保存和 Mock 各有一个总开关，互不代替。

### 按规则保存响应

保存总开关打开后，请求要同时满足下面几项才会落盘：

- URL 命中某条已启用保存规则。匹配是子串，或者写成 `/正则/`、`/正则/i`。
- HTTP 方法命中。方法列表为空表示不限方法。
- 响应 `Content-Type` 能分成 JSON、普通文本或 SSE。图片等二进制，以及分不进这三类的类型，直接跳过。
- 可选的状态码过滤（例如 `200-299,304`）通过。留空表示不限状态码。
- 响应体非空。若规则设置了大小上限（KB），超过上限的跳过；`0` 表示不限，界面上限为 10240 KB。
- 这条响应不是刚刚被本插件 Mock 出去的（见下文）。发往插件内部 SSE 回放端口的请求也不会再保存。

命中后只把**响应体**写成 UTF-8 文本文件，放进该规则自己的绝对路径目录：

- JSON 用 `.json`，文本和 SSE 用 `.txt`。
- 文件名是 `{whistle 用户名前缀}{URL 路径最后一段}_{时间戳}`。用户名前缀来自 whistle 配置里的 `username`，没有则为空。
- JSON 可以按规则选择格式化后再写；解析失败就保留原文。
- 同一条响应可以命中多条保存规则，每条规则各写一份到自己的目录。

目录里另有索引 `.sake-index.json`，给每个文件记下：来源 URL、`Content-Type`、方法、保存时间。索引最多留 500 条，按时间留较新的；更旧的条目会从索引删掉，对应文件还在。索引写失败不影响文件本身。

配置界面可以增删改、启用或停用、排序、复制保存规则，按名称或匹配串筛选，并维护最近用过的目录。改完要点「更新配置」（或 ⌘/Ctrl + S）才写入存储。规则条数上限 200。

### 用文件 Mock 请求

Mock 总开关打开后，按规则列表顺序找**第一条**同时满足这些条件的已启用规则：URL 命中该规则自己的 pattern、方法命中、目录和文件列表可用。命中率默认 100；调低后按概率放行，没命中就当这条规则没生效，请求继续走真实服务器。

命中之后：

- 从这条规则事先勾选的文件里取一个。模式为固定（永远用列表第一个）、轮换或随机。一条规则最多 20 个文件。轮换进度只在进程内存里，重启清零，界面可以重置。
- JSON / 文本一次性返回文件内容。规则上的延迟（默认 50ms，最大 5000ms）和抖动会加到响应上。
- SSE 交给本机 `127.0.0.1` 上的内部服务，按事件逐段推。该服务还没就绪时，退化为一次性返回。
- 状态码默认 200，只有规则里改成非 200 才会覆盖。响应头由规则另配，并带上按类型合成的 `Content-Type`（JSON、纯文本或 `text/event-stream`）和 `cache-control: no-store`。
- 文件名含空白或 `>` 时，改为把文件内容塞进 whistle 规则值，避免路径写进规则出错。

Mock 规则的 pattern、方法、目录都要单独配置。文件必须在界面里勾选，勾选列表可以按文件名或索引里的来源 URL 搜索。来源 URL、方法、大小、时间只用于展示和搜索。

从一条保存规则点「生成 Mock」时，会带上名称、pattern、方法、目录，并按保存类型猜一个 Mock 类型（优先 SSE，其次 JSON，否则文本）。文件列表是空的，状态码 200，延迟等用默认值。用户还要自己勾选文件并更新配置，这条 Mock 规则才会参与回放。

被 Mock 命中的 URL 会在进程内存里记一笔，约 60 秒内、最多约 1000 条。保存逻辑看到这个标记就不再把该 URL 的响应写回去。标记按 URL 字符串，不区分方法。

## 相对目标的缺口

### 目标 1：保存成可回放的文件

「指定规则命中后，把响应体写成文件」已经有了。这些文件也已经被现有 Mock 规则拿来当响应体用。

和「一份可以靠它把当时的响应放回去」相比，现在的文件并不是一次完整交换：

- 文件里只有响应体。抓包时的状态码只参与过滤，不写入文件，也不写入索引。
- 响应头不落盘。索引里的 `Content-Type` 只给界面看、帮着推断类型。回放时的 `Content-Type` 按 Mock 规则的类型重写，不使用抓到的原始头。
- 请求头、请求体都不保存。
- 文件名是路径末段加时间戳，不是这条 URL 的稳定标识。要对回来源 URL，得靠索引。
- 空响应体不保存。图片等二进制不保存。
- 索引只保留较新的 500 条来源信息。更旧的文件还在目录里，但索引里已经没有它的 URL。

这些算不算「还不能回放」，取决于回放要保真到哪一步。本文不把某一种保真度写成已定需求，见「待确认」。

### 目标 2：按 URL 自动匹配保存结果并回放

这一条目前没有。

现在的回放匹配的是 **Mock 规则上填写的 pattern**，然后在 **用户勾选的文件** 里按固定 / 轮换 / 随机挑一个。索引里记下的那次请求 URL 不参与运行时查找。因此：

- 只保存、不另写 Mock 规则并勾选文件，之后的请求不会自动用到这些文件。
- 「生成 Mock」也不会按已保存的 URL 把文件绑上去。
- 一条保存规则的 pattern 往往宽于某一次具体 URL。勾进同一条 Mock 规则的文件可以来自不同 URL，回放时不会再按当前请求的 URL 挑对应的那一份。
- 同一个 URL 被反复保存成多份文件时，没有「按这个 URL 决定回放哪一份」的规则。现有固定 / 轮换 / 随机作用在勾选列表上，不作用在「这个 URL 的保存历史」上。

## 要补齐的结果

在上面的现状之上，用户要的结果是：

1. 指定规则命中的抓包响应，能落成之后可以回放的文件。现状已经能落响应体；若回放还需要当时的状态码、响应头或其他字段，补哪些、以什么形式落盘，见待确认，本文不规定。
2. 这些文件保存之后，后续请求能按 URL 自动找到对应的保存结果并回放，而不必为每一次捕获再手动勾选文件。

现有的「手写 Mock 规则、勾选文件、固定 / 轮换 / 随机」仍然是今天的行为。自动按 URL 回放要不要另开一条路、要不要替换这条路、两者撞上时听谁的，都还没定。

下面每条都还没有产品结论。实现时不要把其中某一项当成已经同意的方案。

1. **怎样算「按 URL 匹配上」**  
   和索引里那次请求的 URL 全等、去掉 query、只比路径，还是继续用现在的子串或 `/正则/i`？要不要区分末尾斜杠、大小写、默认端口？

2. **同一个 URL 保存了多份时回放哪一份**  
   最新、最早、按 HTTP 方法再分，还是固定 / 轮换 / 随机？多条保存规则把同一次响应写进不同目录时，以哪一份为准？

3. **自动回放和现有 Mock 规则如何并存**  
   是在现有规则之外增加「按已保存 URL 自动回放」，还是改变现在必须勾选文件的方式？两条都能命中时谁优先？只打开保存、只打开 Mock、两个都开，各自应发生什么？

4. **匹配键除了 URL 还包含什么**  
   相同 URL、不同方法，或相同 URL、不同请求体，算不算同一次可回放的请求？现状索引有方法、没有请求体。

5. **回放要还原哪些内容**  
   只还原响应体（现状大致如此，但状态码默认 200、响应头按规则重写），还是连原始状态码、原始响应头一起还原？请求头和请求体要不要进入保存文件？

6. **自动匹配失败时怎么办**  
   没有对应保存结果、文件丢了、或索引里已经没有这条 URL 时，是继续访问真实服务器（现有 Mock 未命中时就是这样），还是返回错误？

7. **哪些响应必须变成可回放文件**  
   空响应体、图片和其他二进制、超过大小上限的响应，现在都会跳过。这些是否纳入目标 1，没有结论。

8. **来源 URL 从索引里被裁掉之后还要不要能对上**  
   索引最多 500 条。自动匹配若依赖这份索引，更旧的文件会按 URL 对不上。是否接受，还是匹配必须能找回这些文件，没有结论。

9. **回放结果要不要再次被保存**  
   现在被 Mock 的 URL 大约 60 秒内不会再保存，且只按 URL 记、不按方法记，进程重启后标记消失。自动回放开着时是否保持「回放不再入库」，没有结论。
